# Нативная загрузка видео в Дзен через локальный Яндекс.Браузер

Этот документ описывает канонический browser-upload алгоритм локального
NotebookLM-video downstream. Штатный путь запускается через
`run-worker.cmd -> full-worker.js -> scheduled-worker.js`; ручные
`run-dzen-publish.cmd` и `run-dzen-dry-run.cmd` остаются операторскими и
диагностическими entrypoint.

Все Dzen-пути используют один защищённый профиль Яндекс.Браузера и общий CDP
bootstrap. Профиль, cookies и сессии нельзя удалять или пересоздавать автоматикой.
Native Dzen upload является штатной локальной scheduled-фазой, но остаётся
отдельным downstream относительно nightly GitHub production и не меняет RSS.

## Канонический live-flow

Перед любым новым upload выполняется fail-closed duplicate guard:

```text
Studio -> Публикации -> Видео
  -> input[type="radio"][aria-label="Видео"]
  -> checked=true
  -> искать title prefix до " | "
```

Если ожидаемый prefix найден, лог содержит `ВИДЕО УЖЕ ЕСТЬ`, а новый draft, MP4
upload и publish click не выполняются.

Если опубликованное видео отсутствует и job действительно имеет статус PENDING
**без закреплённого draftId**, допускается один fresh upload. Во всех иных
случаях никакого нового MP4 upload:

```text
PENDING -> UPLOAD_ARMED (записать ДО upload)
 -> MP4 upload
 -> remote videoEditorPublicationId -> DRAFT_CREATED (сохранить ID немедленно)
 -> title/description один раз
 -> PNG cover один раз
 -> ровно 5 tag-chip
 -> metadata/cover/tags подтверждены -> DRAFT_PROCESSING
 -> ждать «Загрузили и обработали видео» + «Готово: можно публиковать и смотреть»
 -> если обработка дольше окна: завершить child без click; следующий scheduled запуск
    открывает ТОЛЬКО сохранённый draftId, проверяет URL/title/description и продолжает ждать
 -> comments = «Все пользователи»
 -> CLICKED_UNVERIFIED (сохранить ДО браузерной попытки клика)
 -> один клик обычной кнопки «Опубликовать»/«Отправить»
 -> 45 секунд read-only наблюдения + локальный диагностический PNG
 -> 45-секундное post-click наблюдение с опросом разрешённых уведомлений
 -> read-only проверка опубликованного списка И существования конкретного draftId
 -> PUBLISHED только после подтверждения
```

Кнопка «Опубликовать после обработки» намеренно не используется. При сомнениях
в принадлежности открытого редактора, неполной metadata, исчезновении draftId,
или неопределённости исхода клика автоматизация прекращает мутирующие действия.
Inter-run resume разрешён только для DRAFT_PROCESSING с сохранённым ID.
Ранее созданные черновики без checkpoint автоматически не подхватываются.

## At-most-once state machine

Scheduled orchestration сохраняет `UPLOAD_ARMED` **до** запуска live child; `DRAFT_CREATED` с точным ID сохраняется сразу после создания удалённого черновика, а `DRAFT_PROCESSING` только после подтверждения metadata/cover/tags.
Дальнейшая схема:

```text
PENDING -> UPLOAD_ARMED -> DRAFT_CREATED -> DRAFT_PROCESSING
 DRAFT_PROCESSING -> при необходимости продолжить ТОЛЬКО pinned draftId
 DRAFT_PROCESSING -> CLICKED_UNVERIFIED (до клика)
 CLICKED_UNVERIFIED -> read-only verification -> PUBLISHED

UPLOAD_ARMED / DRAFT_CREATED / legacy RETRYABLE_PRE_CLICK /
legacy PUBLISH_ARMED / CLICKED_UNVERIFIED / BLOCKED_AMBIGUOUS
 -> только read-only verification или ручная диагностика
 -> ни нового MP4 upload, ни повторного publish click
```

Сообщение `publishClicked=false` **само по себе не подтверждает отсутствие
удалённого черновика**, поэтому больше не разрешает fresh retry. Отдельное
состояние DRAFT_PROCESSING отличает успешно подготовленный, но пока ещё
обрабатываемый черновик от любого неопределённого результата upload.

## Post-click: универсальный обработчик уведомлений

`dzen-browser-runner.js` теперь только запускает дочерний процесс, обрабатывает
завершение и тайм-аут, защищает браузерный профиль и журналирует ошибки.
В нём нет конкретных названий проверочных окон, их обнаружения, ручного
ожидания, восстановления окна или дополнительных циклов после завершения child.

Сразу после единственного publish-click `dzen-publish-direct.js`
сохраняет прежнее **45-секундное наблюдение** без повторных кликов
публикации. В каждом проходе наблюдения вызывается
`dzen-safe-notices.processKnownDzenNotices(browser, logger)`, включая
ситуацию, когда исходная страница редактора уже закрылась.
Это расширяемая точка только для заранее известных, безопасных
информационных уведомлений; на данный момент разрешён только точный
флажок `Больше не показывать такие сообщения` у сообщения
`Видео загружено за N сек`. Обработчик использует максимум одну попытку
за browser session и не блокирует общий сценарий при отсутствии окна.

Все прочие окна, в том числе проверки пользователя, оставляются
оператору. Специального ожидания таких окон нет: если внешняя платформа
не завершила публикацию, её исход остаётся `CLICKED_UNVERIFIED`,
с запретом второго upload и второго publish-click. Итог по-прежнему
подтверждается точным опубликованным public ID, а не исчезновением черновика.

## Browser bootstrap

`dzen-browser-runner.js` использует `browser-session.js` и тот же защищённый
профиль, что NotebookLM worker. До Dzen-фазы NotebookLM browser/CDP должен быть
закрыт. Dzen bootstrap не удаляет и не пересоздаёт профиль или session files.

Штатный браузер может запускаться свёрнутым. Runner специально не
разворачивает его ради неизвестных окон: пользователь самостоятельно
управляет такими окнами. Автоматический handler не переключает на них фокус.

## Метаданные

Заголовок:

```text
ИИ-Сводка на <длинная русская дата> | Подпишись, чтоб получать свежее!
```

Описание формируется один раз. Ссылки после `Этот выпуск:` находятся на
отдельных bullet-строках. Whitespace-only изменения, внесённые Дзеном, не
запускают повторный `fill()`; изменение непробельного содержимого остаётся
ошибкой.

## Теги

Обязательны ровно пять отдельных tag-chip:

```text
ии
ai
полезныесоветы
будущее
лайфхак
```

После Enter DOM может перерисоваться, поэтому input при необходимости ищется
заново. Исчезновение input после пятого тега нормально только когда все пять
ожидаемых chip уже видимы.

## Готовность и комментарии

Раннее `Уже можно публиковать` не является финальной готовностью. Перед
единственным publish click одновременно требуются:

- `Загрузили и обработали видео`;
- `Готово: можно публиковать и смотреть`;
- активная точная кнопка `Опубликовать` или `Отправить`.

После этого выставляется `Кто может комментировать = Все пользователи`, кнопка
проверяется ещё раз и нажимается ровно один раз.

## Логирование

Основные markers:

```text
ВИДЕО УЖЕ ЕСТЬ
КЛИК ПУБЛИКАЦИИ ВЫПОЛНЕН ОДИН РАЗ
ПОСЛЕ PUBLISH ПОЯВИЛАСЬ АНТИБОТ-ПРОВЕРКА «Я НЕ РОБОТ»
Антибот-проверка исчезла
```

Blocking errors пишутся с `!!! DZEN:`. Если ручной challenge не снят за 120
секунд, ошибка обязана явно указывать, что publish click уже состоялся и
повторный click запрещён.

## Ручной запуск

```powershell
cd "C:\TRASH\NotebookLMBot"
.\run-dzen-publish.cmd --date=YYYY-MM-DD
```

`run-dzen-dry-run.cmd` не выполняет финальный publish click и не является
каноническим scheduled алгоритмом.

allowlist: только точный флажок `Больше не показывать такие сообщения`.
Окна проверки человека не обходятся и не подтверждаются автоматически.
