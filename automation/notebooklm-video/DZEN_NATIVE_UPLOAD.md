# Нативная загрузка видео в Дзен через локальный Яндекс.Браузер

Этот документ описывает **экспериментальный операторский** browser-upload путь
для уже готового NotebookLM MP4. Он использует тот же защищённый профиль
Яндекс.Браузера и тот же проверенный browser/CDP bootstrap, на котором работает
локальный `worker.js`.

Путь пока **не подключён** к обычному `worker.js`, `run-worker.cmd`,
`run-worker-hidden.vbs` или Планировщику Windows. Обычный запуск NotebookLM worker
не публикует видео в Дзен. Финальная публикация выполняется только отдельной
явной операторской командой `run-dzen-publish.cmd`.

## Browser bootstrap

Операторские Dzen-команды больше не требуют предварительного ручного запуска
Яндекс.Браузера и не используют `open-robot-browser.ps1` / `open-robot-browser.cmd`
как основной путь.

`run-dzen-publish.cmd` и `run-dzen-dry-run.cmd` запускают
`dzen-browser-runner.js`, который использует `browser-session.js`. Этот модуль
повторяет рабочий lifecycle `worker.js`:

- тот же `browserExecutable`;
- тот же защищённый `browserProfile`;
- тот же `browserDebugHost` / `browserDebugPort`;
- те же Chromium-флаги, включая background/renderer safeguards;
- ожидание `/json/version` до `browserStartupTimeoutMs`;
- `chromium.connectOverCDP(endpoint)` без прежнего 3-секундного timeout;
- использование существующего persistent browser context;
- закрытие браузера через CDP после завершения операторской команды.

Dzen bootstrap **не удаляет и не пересоздаёт browser profile**, cookies, Google
session, Dzen session или session-файлы профиля.

Прямой запуск `dzen-publish.js` / `dzen-publish-live.js` остаётся внутренним
implementation detail. Канонический операторский вход — только `.cmd`-команды
через `dzen-browser-runner.js`.

## Операторское окно ожидания

После запуска Dzen flow браузер не закрывается из-за первой промежуточной ошибки.
`dzen-browser-runner.js` держит единое операторское окно **до 10 минут** и внутри
него повторяет тот же идемпотентный flow через уже открытый persistent context.

Это особенно важно после выбора большого MP4: форма Дзена может несколько раз
перерисоваться, а Playwright-операция может завершиться раньше, чем серверная
загрузка и создание draft фактически закончатся.

Если за 10 минут публикационный flow не дошёл до подтверждённого результата,
runner завершает дочернее дерево Node-процессов и только после этого закрывает
роботизированный Яндекс.Браузер. То есть короткий selector/input race больше не
приводит к мгновенному закрытию окна через секунду после появления формы.

## Подтверждённый ручной сценарий 27.08.2026

На канале «Заметки из подпространства» проверено:

1. Дзен-студия открывается в защищённом профиле Яндекс.Браузера.
2. Кнопка создания публикации открывает меню с пунктом «Загрузить видео».
3. Локальный MP4 выбирается через стандартный file input.
4. После выбора MP4 создаётся URL с `videoEditorPublicationId`.
5. Форма «Публикация видео» содержит название, описание, обложку, теги и
   настройку «Кто может комментировать».
6. Локальный PNG принимается как пользовательская обложка без обязательного
   дополнительного кадрирования.
7. После обработки Дзен показывает «Загрузили и обработали видео» и активирует
   кнопку «Опубликовать».
8. Ручная публикация этим путём появилась именно в разделе **«Видео»**.

Это текущий эталонный UI-сценарий. RSS-путь для нативного Video ранее закрыт как
неуспешный, см. `DZEN_VIDEO_EXPERIMENTS.md`.

## Реализация

Подготовительный helper `dzen-publish.js`:

- запускается с `--dry-run`;
- берёт выпуск из `state.json` по дате;
- использует `job.downloadedFile` как локальный MP4;
- использует `job.previewFile` или соседний PNG; если PNG отсутствует, создаёт его
  через уже установленный `ffmpeg-static`;
- подключается к уже запущенному `browser-session.js` роботизированному
  Яндекс.Браузеру по CDP;
- проверяет авторизацию и имя канала;
- выбирает «Загрузить видео»;
- для MP4 предпочитает прямой `input[type=file].setInputFiles()`, а filechooser
  оставляет fallback-путём;
- не считает ранний timeout/error `setInputFiles` достаточным доказательством,
  что upload провалился: после него продолжает ждать появления
  `videoEditorPublicationId`;
- сохраняет `videoEditorPublicationId` и draft URL в `state.json`;
- ждёт стабилизации формы и дозаполняет название/описание при её перерисовке;
- при проверке metadata нормализует служебные различия пробелов и переносов строк,
  но по-прежнему требует наличие полного ожидаемого текста;
- загружает PNG через «Добавить обложку»;
- добавляет ровно пять тегов и после каждого подтверждает отдельную tag-chip;
- при необходимости кликает точную popup-подсказку;
- отдельно проверяет, что пятый тег реально добавлен;
- пытается выставить «Кто может комментировать» = «Все пользователи»;
- если dropdown комментариев не удалось переключить, продолжает и пишет в общий
  `worker.log` строку с префиксом `!!! DZEN:`;
- ждёт состояния «Загрузили и обработали видео» и активной кнопки
  «Опубликовать»;
- сохраняет diagnostic screenshot и статус `READY_TO_PUBLISH`.

Финальный helper `dzen-publish-live.js` затем:

1. переиспользует подготовительный flow;
2. перед кликом открывает Studio → «Публикации» → «Видео» и считает уже
   существующие записи с тем же заголовком;
3. сохраняет этот baseline в `state.json` и переводит job в `PUBLISHING`;
4. нажимает **«Опубликовать»**;
5. сразу переводит состояние в `PUBLISH_CLICKED_UNVERIFIED`;
6. повторно проверяет вкладку **«Видео»**;
7. помечает job как `PUBLISHED` только если число одноимённых записей стало больше
   сохранённого baseline;
8. сохраняет screenshot результата и найденный URL, если его удалось извлечь из
   Studio.

Проверка по увеличению числа одноимённых строк нужна потому, что тестовый выпуск
27 августа уже имеет вручную опубликованное видео с тем же заголовком. Простая
проверка «такой заголовок есть» дала бы ложный успех.

## Восстановление после timeout загрузки MP4

На Яндекс.Браузере через CDP наблюдалась ситуация, когда Playwright завершал
`fileChooser.setFiles` по timeout, хотя сам MP4 продолжал загружаться и Дзен уже
создавал рабочий video draft.

Поэтому ранняя ошибка передачи файла сама по себе не завершает flow. Код ждёт до
10 минут появления URL с `videoEditorPublicationId`.

Если дочерний Dzen-процесс всё же завершился до того, как успел сохранить draft в
`state.json`, runner проверяет уже открытые страницы persistent context. Если
найден URL с `videoEditorPublicationId`, runner:

1. сохраняет этот **уже существующий** draft в `job.dzenVideo`;
2. выставляет `status=DRAFT_CREATED` и диагностический
   `recoveredAfterUploadTimeout=true`;
3. пишет заметный лог `!!! DZEN:`;
4. повторяет тот же flow внутри оставшегося 10-минутного окна;
5. не создаёт новый video draft только из-за преждевременного Playwright timeout.

## Пустой сохранённый draft

Отдельно подтверждён случай, когда `videoEditorPublicationId` уже появился, но
после аварийного закрытия браузера удалённый draft остался пустой оболочкой без
видео и metadata.

Перед повторным использованием `DRAFT_CREATED` runner открывает сохранённый URL.
Если draft старше минуты и дважды подряд остаётся на исходной форме с кнопкой
**«Выбрать видео»**, он считается явно пустым:

- такой draft **не удаляется автоматически в Дзене**;
- его ID/URL сохраняются в `previousDrafts` локального state;
- текущая ссылка сбрасывается;
- следующий проход создаёт новый video draft и повторно загружает локальный MP4.

Эта проверка не применяется к `READY_TO_PUBLISH`, `PUBLISHING`,
`PUBLISH_CLICKED_UNVERIFIED` или `PUBLISHED`, чтобы не ослаблять защиту от
повторного финального клика.

## Защита от повторного клика

Если после нажатия кнопки новая строка не появилась в течение контрольного окна,
сохраняется `PUBLISH_CLICKED_UNVERIFIED`. Повторный запуск **не нажимает кнопку
ещё раз**, а только повторяет проверку вкладки «Видео».

Это не запрещает публикацию. Это защищает от создания дублей в ситуации, когда
клик мог сработать, а Studio обновилась с задержкой или проверка оборвалась.

Если состояние уже `PUBLISHED`, повторный операторский запуск является no-op.

## Метаданные

Название строится по дате выпуска:

```text
ИИ-Сводка на 27 августа 2026 | Подпишись, чтоб получать свежее!
```

Описание:

```text
Что происходит в мире Искусственного Интеллекта (ИИ, AI) и Нейросетей на текущий момент - коротенько о самом главном

Без рекламы и воды на 27.08.2026:
- Глобальные новости
- Новости ИИ России
- Выводы и тренды

Этот выпуск:
https://rybalka.one/posts/2026-08-27/
https://dzen.ru/suite/7971db4c-2a4e-449f-b8bf-c3907486d6f1
```

Дата и URL выпуска берутся из выбранного job, а не зашиваются на 27 августа.

Текущие пять тегов:

```text
ии
ai
полезныесоветы
будущее
лайфхак
```

## Ручной запуск

Единственная команда реальной публикации:

```powershell
cd "C:\TRASH\NotebookLMBot"
.\run-dzen-publish.cmd --date=2026-08-27
```

Если `--date` не указан, используется текущая дата по `timeZone`.

Для диагностики без финального клика:

```powershell
.\run-dzen-dry-run.cmd --date=2026-08-27
```

Предварительно запускать браузер, CDP или PowerShell launcher вручную не нужно.

## Что смотреть после запуска

Основные признаки успеха:

- после MP4 появляется `videoEditorPublicationId`;
- metadata не считаются ошибочными из-за одной мгновенной перерисовки формы;
- в `worker.log` есть подтверждение пяти tag-chip;
- для комментариев либо подтверждено «Все пользователи», либо есть заметная
  non-fatal строка `!!! DZEN:`;
- после клика состояние проходит через `PUBLISHING` /
  `PUBLISH_CLICKED_UNVERIFIED`;
- итоговый статус `PUBLISHED` ставится только после подтверждения новой записи во
  вкладке «Видео»;
- в `screenshotsDir` есть контрольный `dzen-published-video-...png`.

Если helper завершился в `PUBLISH_CLICKED_UNVERIFIED`, повторный запуск не должен
создавать ещё одну публикацию: он только повторяет проверку результата.

## Граница текущего эксперимента

Этот код уже способен выполнить реальный финальный клик, но всё ещё остаётся
**отдельной операторской экспериментальной командой**. В этом изменении он не
становится частью обычного `worker.js` и не запускается Планировщиком Windows.

После живого автоматического теста и обратной связи отдельно принимается решение
о promotion: подключать ли native Dzen upload как следующий идемпотентный этап
обычного локального NotebookLM worker flow.
