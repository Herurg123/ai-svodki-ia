# Автоматизация ИИ-Сводок

Каталог содержит производственный конвейер ежедневной публикации ИИ-Сводок.

## Владение файлами

GitHub Actions управляет:

- `posts/index.html`;
- `posts/rss.xml`;
- `posts/sitemap.xml`;
- `posts/YYYY-MM-DD/index.html`;
- `posts/images/ai-svodka-YYYY-MM-DD.png`.

Исторический пакет `posts/dzen-test/**` сохраняет исходные URL, но подчиняется
тому же 32-дневному окну хранения, что и обычные публичные выпуски.

Главная страница сайта `/index.html` не входит в производственный контур ИИ-Сводок.

## Каталоги данных

### `content/YYYY-MM-DD/`

Структурированные материалы выпуска. Для архива без повторной публикации достаточно:

- `meta.json`;
- `stories.json`.

Полный производственный выпуск дополнительно содержит статью, источники, digest и обложку.

Ночной `repository-cleanup.yml` компактирует выпуски, дата которых строго
старше 32 полных календарных дней. Он сохраняет `meta.json` и `stories.json`,
поэтому редакционная дедупликация продолжает работать.

Тот же запуск атомарно удаляет из `posts/` старые страницы и обе копии legacy-
обложек, оставляет в RSS только актуальные ссылки и пересобирает
`posts/index.html`, `posts/dzen-test/index.html`, оба RSS и sitemap. После
успешного commit отдельный job синхронизирует на FTP именно созданный SHA.
Если проверка, commit или FTP завершаются ошибкой, русская Actions Summary
явно показывает, на каком состоянии остановился запуск.

### `archive/index.json`

Собирается скриптом `bootstrap_archive.py` из рабочего RSS и всех датированных каталогов `content/`. Архивные content-only записи включаются даже тогда, когда соответствующей статьи нет в RSS. Этот файл используется для поиска повторов и определения обновлений ранее опубликованных сюжетов.
Для каждого доступного выпуска архив также хранит `search_cutoff_at`: сначала
берётся сохранённый конец research-окна, для старых artifacts — `run-info.json`
`started_at`, и лишь при отсутствии обоих используется `published_at`.

### `preview/`

Временные результаты dry-run и отчёты CI. Каталог создаётся динамически,
его содержимое в Git не хранится.

## Workflow

В репозитории остаются четыре понятные точки входа:

- `ci.yml` — единая офлайн-проверка `main`: Python, unit-тесты, архив, production-контракт, RSS, sitemap и Schema.org;
- `daily-production.yml` — ежедневное исследование, редактура, обложка, сборка и публикация;
- `repository-cleanup.yml` — единая ночная очистка рабочих материалов, публичных страниц, RSS и sitemap старше 32 дней;
- `deploy-posts.yml` — единственная FTP-синхронизация каталога `posts/`, включая контролируемые удаления.

Экспериментальные preview, fixture, recovery и pre-production workflow удалены. Их полезные проверки остаются в `automation/tests/` и выполняются единым CI.

## Расписание и режимы запуска

`daily-production.yml` имеет три страховочных cron-окна: `23:17`, `23:37` и
`23:57 UTC` предыдущего календарного дня, то есть `02:17`, `02:37` и
`02:57 Europe/Moscow` даты выпуска. GitHub Actions может поставить schedule в
очередь и фактически начать его позднее. Все три окна защищены одним gate:

- если выпуск уже есть в RSS и на живом сайте, запуск завершается бесплатным
  no-op;
- если выпуск есть в GitHub, но живой URL недоступен, выполняется только
  FTP-redeploy точного commit;
- только отсутствие выпуска разрешает research и остальные платные этапы.

Плановый запуск всегда работает с `publish=true`. У ручного
`workflow_dispatch` доступны три входа:

- `publication_date` — необязательная дата `YYYY-MM-DD`;
- `publish` — по умолчанию `false`, поэтому ручной запуск является dry-run;
- `recovery_run_id` — необязательный ID запуска с сохранённым оплаченным
  artifact.

Без явного `recovery_run_id` workflow сам ищет пригодный artifact той же даты.
Он может переиспользовать полный, частичный или research-only результат и уже
сгенерированную обложку. Если основной Responses-запрос завершился и выполнил
Web Search, но вернул нулевой первичный пул, этот research-only artifact не
считается техническим сбоем: workflow продолжает обязательный coverage audit.
Только нулевой итог после полного audit и обязательного для такого случая
high-signal recall sentinel становится завершённой редакционной остановкой,
которая переиспользуется без нового платного поиска. Production-artifacts
хранятся 14 дней.

Метаданные выпуска нормализуются к 06:00 МСК. Окно research начинается с
фактического `search_cutoff_at` последнего успешно опубликованного выпуска и
заканчивается timestamp, зафиксированным до первого текущего поиска;
пропущенные календарные дни допустимы. Поэтому событие, появившееся после
старта прежнего research, но до его номинальных 06:00, попадёт в следующее
окно.

## Редакционный контракт короткого выпуска

Канонические правила находятся в
[`specs/editorial-policy.md`](specs/editorial-policy.md). Для production
обязательны следующие условия:

- обычная цель — 7–12 сюжетов, но для публикации достаточно одного достойного;
- числовых квот для китайского и российского разделов нет;
- пустые китайский и российский разделы не выводятся;
- выпуск из 1–6 сюжетов публикуется, а первым блоком текста сразу под обложкой
  получает курсивную пометку «Новостей сегодня меньше, чем обычно»;
- coverage audit может дополнить даже нулевой первичный пул; отсутствие
  достойных новостей после завершённой проверки допустимо, но технически
  неполный audit или незавершённый zero-pool recall sentinel блокирует Image
  API, commit и deploy;
- источники являются неизменяемыми данными research: перед валидацией
  метаданные известного нормализованного URL восстанавливаются из
  `candidates.json`, а неизвестный URL или ссылка вне исследовательского пула
  по-прежнему блокируют выпуск.

Для короткого пула coverage audit выполняет шесть обязательных отдельных
проверок: security для мира, России и Азии; legal/copyright/scraping;
проверяемый curiosity; авторитетный last-mile sweep оставшихся пробелов
research. Последний проход использует фильтр первоисточников, агентств, судов,
регуляторов и профильных изданий; Reuters — приоритетный, но не единственный
источник. Каждый проход ограничен одной завершённой операцией `search`, общий
предел — 7. Седьмой слот сначала является резервом для первой незавершённой
обязательной проверки. Если все шесть успешно завершены, но пригодный пул
остаётся нулевым, резерв превращается в `high_signal_recall_sentinel`: один
компактный агентский поиск с доменным фильтром Reuters/AP/Bloomberg/FT. Он не
увеличивает лимит 7 и не запускается при ненулевом пуле.

`open_page` и `find_in_page` видны в диагностике, но не считаются поисками.
Повторный editorial из-за audit или sentinel разрешён лишь после фактического
добавления пригодного кандидата. Статусы полноты, фактические запросы/источники
и retrieval-диагностика сохраняются в `coverage-audit.json`. В частности,
`primary_search_retrieval` показывает число фактических search operations,
число логических `action.query/action.queries`, распределение запросов по
операциям и факт batching; `audit_search_retrieval` делает то же для targeted
проходов. Полный контракт описан в
[`specs/editorial-policy.md`](specs/editorial-policy.md).

Основной research ограничен 12 Web Search calls. Внутри того же лимита primary
discovery организован последовательно: широкий мировой sweep,
самостоятельная проверка Reuters/AP/Bloomberg, матрица Китай/Азия × типы
событий, матрица Россия × типы событий, тематические проходы и last-mile,
когда пул остаётся меньше обычной цели. Матрицы требуют покрыть пересечения,
но не выполнять отдельный Web Search для каждой клетки; провайдер может
объединять несколько логических `action.queries` в одну search operation, и
этот batching теперь явно фиксируется в production artifact. Максимальный
бюджет короткого дня не меняется и составляет 19 вызовов: 12 основного
research и до 7 coverage audit. Текущий текстовый контракт принимает
`gpt-5.6-terra`, image-контракт — `gpt-image-2`.

При recovery полный audit не повторяется. Если artifact содержит частичный
план, автоматика сохраняет его запросы и источники, не повторяет уже
завершённые направления и запускает только отсутствующие проверки в остатке
семивызовного бюджета. Успешный recall sentinel записывается как второй проход
`general_coverage_gaps` со стратегией `high_signal_recall_sentinel`, поэтому
его кандидат и поисковая траектория также переиспользуются. Технически
незавершённый sentinel не записывается как потраченный обязательный проход:
нулевая остановка остаётся неполной, а следующий recovery-run может повторить
только sentinel, не оплачивая шесть обязательных направлений заново.

## Архив и дедупликация

Перед production-запуском:

```bash
python automation/scripts/bootstrap_archive.py
python automation/scripts/validate_archive.py
```

Архив хранит заголовки, организации, темы, типы событий, краткие описания, ключевые слова и URL источников. Сравнение нового исследования выполняется не только по заголовку, поэтому содержание `stories.json` важнее наличия копии старой HTML-страницы.

## Локальная проверка

Минимальная редакционная проверка:

```bash
python -m unittest discover -s automation/tests -v
python automation/scripts/validate_editorial_contract.py
python automation/scripts/validate_archive.py
```

Main CI дополнительно компилирует Python и проверяет production-контракт, RSS,
sitemap и Schema.org. Точный актуальный набор команд находится в
[`../.github/workflows/ci.yml`](../.github/workflows/ci.yml); все эти проверки
офлайн и не используют платные API.
