# Автоматизация ИИ-Сводок

Каталог содержит производственный конвейер ежедневной публикации ИИ-Сводок.

## Владение файлами

GitHub Actions управляет:

- `posts/index.html`;
- `posts/rss.xml`;
- `posts/sitemap.xml`;
- `posts/YYYY-MM-DD/index.html`;
- `posts/images/ai-svodka-YYYY-MM-DD.png`.

Исторический пакет `posts/dzen-test/**` сохраняет исходные URL, но подчиняется
тому же 32-дневному окну хранения, что и обычные публичные выпуски.

Главная страница сайта `/index.html` не входит в производственный контур ИИ-Сводок.

## Каталоги данных

### `content/YYYY-MM-DD/`

Структурированные материалы выпуска. Для архива без повторной публикации достаточно:

- `meta.json`;
- `stories.json`.

Полный производственный выпуск дополнительно содержит статью, источники, digest и обложку.

Ночной `repository-cleanup.yml` компактирует выпуски, дата которых строго
старше 32 полных календарных дней. Он сохраняет `meta.json` и `stories.json`,
поэтому редакционная дедупликация продолжает работать.

Тот же запуск атомарно удаляет из `posts/` старые страницы и обе копии legacy-
обложек, оставляет в RSS только актуальные ссылки и пересобирает
`posts/index.html`, `posts/dzen-test/index.html`, оба RSS и sitemap. После
успешного commit отдельный job синхронизирует на FTP именно созданный SHA.
Если проверка, commit или FTP завершаются ошибкой, русская Actions Summary
явно показывает, на каком состоянии остановился запуск.

### `archive/index.json`

Собирается скриптом `bootstrap_archive.py` из рабочего RSS и всех датированных каталогов `content/`. Архивные content-only записи включаются даже тогда, когда соответствующей статьи нет в RSS. Этот файл используется для поиска повторов и определения обновлений ранее опубликованных сюжетов.
Для каждого доступного выпуска архив также хранит `search_cutoff_at`: сначала
берётся сохранённый конец research-окна, для старых artifacts — `run-info.json`
`started_at`, и лишь при отсутствии обоих используется `published_at`.

### `preview/`

Временные результаты dry-run, CI и repository-hygiene. Каталог создаётся
динамически, его содержимое в Git не хранится.

### `recovery/`

Временная рабочая зона восстановленных production-artifacts. Она не является
частью канонического состояния проекта и игнорируется Git.

## Workflow

В репозитории остаются пять понятных точек входа:

- `ci.yml` — единая офлайн-проверка `main`: Python, unit-тесты, архив, production-контракт, RSS, sitemap и Schema.org;
- `daily-production.yml` — ежедневное исследование, редактура, обложка, сборка и публикация;
- `repository-cleanup.yml` — единая ночная очистка рабочих материалов, публичных страниц, RSS и sitemap старше 32 дней;
- `repository-hygiene.yml` — отдельная инженерная уборка GitHub: merged-ветки, безопасные Actions artifacts и orphaned workflows, без изменения tracked-файлов;
- `deploy-posts.yml` — единственная FTP-синхронизация каталога `posts/`, включая контролируемые удаления.

Перед сборкой `daily-production.yml` запускает `stage_legacy_images.py` для
совместимости со старыми обложками из `posts/dzen-test/images`. Это best-effort
миграционный слой: отсутствие или файловая ошибка legacy-набора сохраняются в
`legacy-images.json` как warning и сами по себе не блокируют выпуск. Реальным
gate остаётся последующая сборка и валидация canonical `posts/`: если нужной
страницы или картинки действительно нет, publication всё равно остановится.

Экспериментальные preview, fixture, recovery и pre-production workflow удалены. Их полезные проверки остаются в `automation/tests/` и выполняются единым CI.

## Расписание и режимы запуска

`daily-production.yml` имеет один основной GitHub cron: `23:17 UTC`
предыдущего календарного дня, то есть `02:17 Europe/Moscow` даты выпуска.
Независимый резервный запуск остаётся в cron-job.org, поэтому ещё два GitHub
cron-окна больше не создают повторные no-op runs. GitHub Actions может поставить
schedule в очередь и фактически начать его позднее. Основной и резервный
запуски защищены одним gate:

- если выпуск уже есть в RSS и на живом сайте, запуск завершается бесплатным
  no-op;
- если выпуск есть в GitHub, но живой URL недоступен, выполняется только
  FTP-redeploy точного commit;
- только отсутствие выпуска разрешает research и остальные платные этапы.

Перед новым research канонические файлы предыдущего выпуска в GitHub остаются
жёсткой проверкой непрерывности. Дополнительная проверка его статьи и обложки
на живом сайте теперь диагностическая: временный сетевой, FTP- или CDN-сбой
сохраняется в `previous-release.json` как warning и не блокирует независимую
сборку следующего выпуска.

Плановый запуск всегда работает с `publish=true`. У ручного
`workflow_dispatch` доступны три входа:

- `publication_date` — необязательная дата `YYYY-MM-DD`;
- `publish` — по умолчанию `false`, поэтому ручной запуск является dry-run;
- `recovery_run_id` — необязательный ID запуска с сохранённым оплаченным
  artifact.

Без явного `recovery_run_id` workflow сам ищет пригодный artifact той же даты.
При нескольких вариантах он сначала выбирает наиболее полный: artifact с
валидированной обложкой, затем с готовым digest, затем research-only; дата
создания используется только для выбора между artifacts одинаковой полноты.
Так recovery не откатывается на более бедный результат и не повторяет уже
оплаченные coverage/editorial/image стадии. Для полностью готового recovery,
которому больше не нужны coverage/editorial/Image API, OpenAI SDK и
`OPENAI_API_KEY` не являются искусственным gate. Если текстовый artifact уже
готов, но обложка отсутствует, workflow не устанавливает текстовый OpenAI SDK:
он проверяет только ключ и image-модель и выполняет один Images API запрос.
Если основной Responses-запрос завершился и выполнил
Web Search, но вернул нулевой первичный пул, этот research-only artifact не
считается техническим сбоем: workflow продолжает обязательный coverage audit.
Только нулевой итог после полного audit и актуального zero-pool recall sentinel
становится завершённой редакционной остановкой, которая переиспользуется без
нового платного поиска. Такая остановка завершает production успешно как `no-publish`;
после неё не запускаются Image API, commit и deploy. Технически неполный audit
по-прежнему завершает job ошибкой. Production-artifacts создаются с `retention-days: 14`,
но `repository-hygiene.yml` может удалить уже ненужные опубликованные варианты
раньше по безопасному окну выпусков; актуальная неопубликованная дата остаётся
защищена для recovery.

Метаданные выпуска нормализуются к 06:00 МСК. Окно research начинается с
фактического `search_cutoff_at` последнего успешно опубликованного выпуска и
заканчивается timestamp, зафиксированным до первого текущего поиска;
пропущенные календарные дни допустимы. Поэтому событие, появившееся после
старта прежнего research, но до его номинальных 06:00, попадёт в следующее
окно.

## Repository hygiene

`repository-hygiene.yml` запускается ежедневно в `12:43 UTC`, то есть
`15:43 Europe/Moscow`, далеко от 01:43 content cleanup и 02:17 production.
Плановый запуск применяет доказуемо безопасные операции автоматически;
ручной `workflow_dispatch` по умолчанию работает как audit-only и включает
удаления только при `apply=true`.

Алгоритм разделён на `repository_hygiene_policy.py` с чистыми правилами
классификации, `repository_hygiene_github.py` с минимальным GitHub REST-клиентом
и `repository_hygiene.py` с plan/apply runtime. Каждый apply-job заново строит
план и проверяет SHA `main`; изменение `main` во время destructive-фазы
останавливает запуск.

### Ветки

- защитное окно — пять последних PR, смёрженных в `main` по `merged_at`;
- `main`, protected branches, ветки открытых PR и ветки с живым Actions-run
  сохраняются;
- старая merged-ветка удаляется только при точном совпадении текущего HEAD с
  `head.sha` её последнего merged PR;
- branch без PR, closed-unmerged или изменённый после merge остаётся
  `review_only`.

Перед фактическим удалением ветка перечитывается, повторно проверяются открытые
PR, активные runs и HEAD. Поэтому plan не считается разрешением удалить объект,
если состояние GitHub успело измениться.

### Actions artifacts

CI-artifacts имеют имя `main-ci-<sha>`. Защищаются SHA текущего `main`, head и
merge SHA последних пяти merged PR и текущие head SHA открытых PR. Остальные
однозначно superseded CI-artifacts удаляются; artifacts веток с неоднозначной
историей остаются `review_only`.

Для `daily-production-YYYY-MM-DD` применяется окно по выпускам, а не по дням
или PR:

- две последние опубликованные даты сохраняют всю artifact-цепочку;
- даты №3–5 сохраняют только artifact run, где шаг `Commit production release`
  завершился успешно;
- более старые опубликованные artifacts удаляются;
- неопубликованная актуальная/будущая дата защищена;
- историческая неопубликованная дата только диагностируется и автоматически
  не удаляется.

Если в момент Actions-prune есть живой `daily-production.yml`, вся Actions-
уборка пропускается. Неизвестные типы artifacts также не удаляются.

### Orphan workflows и старые runs

Workflow, которого больше нет среди файлов `.github/workflows/` текущего
`main`, отключается только если его последние runs относятся к старой merged-
ветке. Canonical workflows, workflow с живым run и workflow, связанный с
сохраняемой либо неоднозначной веткой, защищены. Для динамического GitHub Pages
workflow используется отдельный gate: он может быть отключён только если
репозиторий сообщает `has_pages=false`.

`in_progress` всегда живой. `queued` старше 14 дней считается зависшим и не
может навечно защищать orphan-workflow. Такие stale runs попадают в отчёт, но
первая версия hygiene их не удаляет.

### Source scan

Скрипты, config, prompts и specs не удаляются автоматически. Scanner ищет
входящие текстовые ссылки во всём `.github` и `automation`, а также README и
`AGENTS.md`, затем использует Git-историю файла и количество merge после его
последнего изменения:

- после пяти merge без ссылок файл попадает в `watchlist`;
- после десяти — в `suspected_orphans`;
- обе категории являются только отчётом.

Любая очистка tracked-файлов по этому отчёту выполняется обычным branch → PR →
CI → diff review → отдельный явный merge. Автоматический hygiene меняет только
разрешённые в `AGENTS.md` ephemeral GitHub objects.

## Редакционный контракт короткого выпуска

Канонические правила находятся в
[`specs/editorial-policy.md`](specs/editorial-policy.md). Для production
обязательны следующие условия:

- обычная цель — 7–12 сюжетов, но для публикации достаточно одного достойного;
- числовых квот для китайского и российского разделов нет;
- пустые китайский и российский разделы не выводятся;
- выпуск из 1–6 сюжетов публикуется, а первым блоком текста сразу под обложкой
  получает курсивную пометку «Новостей сегодня меньше, чем обычно»;
- coverage audit может дополнить даже нулевой первичный пул; отсутствие
  достойных новостей после завершённой проверки допустимо; технически неполный audit блокирует
  Image API, commit и deploy, а незавершённый или устаревший zero-pool recall
  sentinel делает нулевую редакционную остановку непригодной;
- источники являются неизменяемыми данными research: перед валидацией
  метаданные известного нормализованного URL восстанавливаются из
  `candidates.json`, а неизвестный URL или ссылка вне исследовательского пула
  по-прежнему блокируют выпуск.

Для короткого пула coverage audit выполняет шесть обязательных отдельных
проверок: security для мира, России и Азии; legal/copyright/scraping;
проверяемый curiosity; авторитетный last-mile sweep оставшихся пробелов
research. Последний проход использует фильтр первоисточников, агентств, судов,
регуляторов и профильных изданий; Reuters — приоритетный, но не единственный
источник. Каждый проход ограничен одной завершённой операцией `search`, общий
предел — 7. Седьмой слот сначала является резервом для первой незавершённой
обязательной проверки. Если все шесть успешно завершены, но пригодный пул
остаётся нулевым, резерв превращается в `high_signal_recall_sentinel` версии 6:
один компактный source-agnostic Web Search без API domain filter. Prompt
запрещает `site:`/`OR`-конструкции и требует один точный запрос
`OpenAI cybersecurity <UTC date>`. Это не увеличивает лимит 7 и не запускается
при ненулевом пуле.

Source-agnostic режим закреплён после цепочки production-регрессий 8 августа.
Сначала широкий четырёхдоменный sentinel уходил в старые результаты, затем
Reuters-only API filter дал false-zero, а v5 без domain filter уже нашёл свежий
Axios-материал внутри редакционного окна, но отклонил его только потому, что
издатель не Reuters. В v6 источник больше не является искусственным барьером:
пригодны надёжные первичные источники, крупные агентства и авторитетные
технологические/деловые СМИ при соблюдении обычных правил окна, значимости,
верификации и антидублей. Версия sentinel хранится в artifact, чтобы recovery
не принимал старую retrieval-стратегию за актуальную.

`open_page` и `find_in_page` видны в диагностике, но не считаются поисками.
Повторный editorial из-за audit или sentinel разрешён лишь после фактического
добавления пригодного кандидата. Для sentinel дополнительно действует
детерминированный инвариант: у кандидата с `category != legal` поля
`legal_scale`/`legal_scale_reason` нормализуются к `not_applicable`/пустой
строке, поэтому расположение URL в `/legal/` или `/litigation/` не может само
по себе превратить security-событие в legal-кандидата.

Статусы полноты, фактические запросы/источники и retrieval-диагностика
сохраняются в `coverage-audit.json`. Поле `audit_notes` после runtime-нормализации
явно описывает обе допустимые роли седьмого слота: retry незавершённого
обязательного направления либо zero-pool recall sentinel. `primary_search_retrieval` показывает
число фактических search operations, число логических
`action.query/action.queries`, распределение запросов по операциям и факт
batching; `audit_search_retrieval` делает то же для targeted проходов. Полный
контракт описан в [`specs/editorial-policy.md`](specs/editorial-policy.md).

Основной research ограничен 12 Web Search calls. Внутри того же лимита primary
discovery организован последовательно: широкий мировой sweep,
самостоятельная проверка Reuters/AP/Bloomberg, матрица Китай/Азия × типы
событий, матрица Россия × типы событий, тематические проходы и last-mile,
когда пул остаётся меньше обычной цели. Матрицы требуют покрыть пересечения,
но не выполнять отдельный Web Search для каждой клетки; провайдер может
объединять несколько логических `action.queries` в одну search operation, и
этот batching явно фиксируется в production artifact. Максимальный бюджет
короткого дня не меняется и составляет 19 вызовов: 12 основного research и до
7 coverage audit. Текущий текстовый контракт принимает `gpt-5.6-terra`,
image-контракт — `gpt-image-2`.

При recovery полный audit не повторяется. Если artifact содержит частичный
план, автоматика сохраняет его запросы и источники, не повторяет уже
завершённые направления и запускает только отсутствующие проверки в остатке
семивызовного бюджета. Успешный актуальный recall sentinel записывается как
второй проход `general_coverage_gaps` со стратегией
`high_signal_recall_sentinel` и `recall_sentinel_version: 6`; его кандидат и
поисковая траектория переиспользуются. Нулевой artifact без sentinel v6, в том
числе artifact с прежними sentinel v1-v5, намеренно считается незавершённым
один раз: шесть обязательных направлений сохраняются, устаревший седьмой проход
удаляется из восстановленного плана, а освободившийся слот расходуется только
на source-agnostic sentinel v6. Технически незавершённый sentinel также
оставляет нулевую остановку неполной и может быть повторён без оплаты шести
обязательных направлений заново.

Транспортная и диагностическая база предыдущего runtime сохранена в
`ensure_story_coverage_runtime_base.py`; `ensure_story_coverage.py` остаётся
исторической точкой входа и накладывает только версионированную retrieval-
политику поверх этой базы.

## Архив и дедупликация

Перед production-запуском:

```bash
python automation/scripts/bootstrap_archive.py
python automation/scripts/validate_archive.py
```

Архив хранит заголовки, организации, темы, типы событий, краткие описания, ключевые слова и URL источников. Сравнение нового исследования выполняется не только по заголовку, поэтому содержание `stories.json` важнее наличия копии старой HTML-страницы.

## Локальная проверка

Минимальная редакционная проверка:

```bash
python -m unittest discover -s automation/tests -v
python automation/scripts/validate_editorial_contract.py
python automation/scripts/validate_archive.py
```

Main CI дополнительно компилирует Python и проверяет production-контракт, RSS,
sitemap и Schema.org. Точный актуальный набор команд находится в
[`../.github/workflows/ci.yml`](../.github/workflows/ci.yml); все эти проверки
офлайн и не используют платные API.

### Retrieval note: recall sentinel v6

Для нулевого пула версия 6 использует один короткий source-agnostic security-
запрос вида `OpenAI cybersecurity <UTC date>`. Дата берётся из UTC-даты конца
редакционного окна. API-доменный фильтр не используется, и найденный надёжный
материал не отклоняется только потому, что его издатель не Reuters. Эта версия
исправляет подтверждённый production-случай v5, где Web Search поднял свежий
Axios-сюжет в редакционном окне, но Reuters-only инструкция заставила модель
отбросить его. Версия хранится в artifact; zero-pool artifact старой версии
возобновляется только для этого одного седьмого поиска.

## Temporal anchor ночного production

`SEARCH_WINDOW_END_AT` — авторитетное `now` для main research, targeted coverage
audit и recall sentinel. Это защищает запуск около полуночи UTC от ложного вывода,
что московская часть окна следующего календарного дня находится в будущем.
